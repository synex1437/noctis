# Tests

The suite behind the numbers in the README: what each run asks, what CI runs, and what the latest runs measured.

Tests, each asking a different question:

| | |
| --- | --- |
| `node tests/contract.js` | Runs every hook in `hooks/hooks.json` the way Claude Code runs it — resolving `${CLAUDE_PLUGIN_ROOT}`, spawning that command with those arguments. Every other suite runs the platform binary directly with `hook` and a payload, never through the command the manifest declares. It also drives the `bin/noctis` launcher with the kernel's answer, bash's `OSTYPE` and `HOSTTYPE` and a fake `uname` that counts its calls: the kernel's answer wins without `uname`, bash's answer on Linux, MSYS (Git Bash) and Cygwin needs no `uname` either, on macOS the shell's `OSTYPE` alone picks the universal `bin/darwin/noctis` without `uname` whatever `HOSTTYPE` says, `uname` answers once for Linux on both CPUs, macOS on both CPUs (the universal binary either way), Git Bash, MSYS and Cygwin (which get the Windows binary), and it covers an unsupported CPU, a relative path with an exported `CDPATH` and the bare name run from the launcher's own folder. A `hook` and a `statusline` call get `GOMAXPROCS=1` with the `NOCTIS_OWN_GOMAXPROCS` marker, any other command neither, and a `GOMAXPROCS` already set reaches a hook as it is. On a Mac it also runs `bin/darwin/noctis` itself and, through `arch`, each build in it that the Mac can run (x86_64 needs Rosetta on Apple silicon), and where the developer tools are installed `lipo` has to find both builds in it. |
| `node tests/lab.js` | 582 black-box checks on Linux (the 7.0 run) against the binary, with a fake `claude`, `codex`, `agy`, `droid`, `copilot`, `gh` and a usage endpoint in a separate process. Each lab checksums its own snapshot of the tree, so a local build runs as it is and no suite rewrites the repository's `bin/SHA256SUMS`; a suite that crashes after its mock server started exits 1 at once and takes the mock with it. Its lean scenario checks that an installed copy carries the hooks module `hooks/hooks.json` names and, when a `claude` 2.1.281 or newer is on PATH, runs `node tests/lean.js`: `claude plugin validate --strict` on the plugin (which must report the module hooking `session.start`, `session.compact` and `turn.complete`) and on the marketplace, then the kit tests below; otherwise it prints why it skipped them. |
| `node tests/torrent.js` | Thousands of long sessions at once. Asks the two questions only volume answers: does the guard ever let a session past the wall, and what does it cost per hook (the hook process alone, as the host waits on it). |
| `node tests/chaos.js` | The failures a real machine produces: 429/403/500, invalid JSON, a body cut halfway, a chunked response cut before its terminating chunk, TLS that will not negotiate, a genuinely full disk (only with `NOCTIS_CHAOS_FULL_DISK`), and state files written by older versions. |
| `node tests/scheduler.js` | Runs the scheduler a real user on this platform gets: a `systemd-run` stand-in on Linux, a `launchctl` stand-in on macOS, the real Task Scheduler on Windows. A parked session is relaunched by the timer with nobody watching, and cancel removes the entry. On Linux and macOS the launchd plist is also parsed with Python's `plistlib`. The `launchctl` stand-in answers `launchctl list` from the jobs it has loaded, and the job that ran a resume must boot itself out afterwards; the launchd path has run only against this stand-in, never on a real Mac. |
| `node tests/soak.js --days 14 [--hard 1]` | A multi-day run (7 days by default, 14 here) of two accounts; `--hard 1` injects 22 kinds of chaos. Hook latencies are the hook process alone, as the host waits on it; a hook other than the blind probe that holds the host as long as a usage fetch that times out is an anomaly. The `claude` a runner launches answers in the session's transcript, says nothing, fails, or answers a moment after it exits, as the seed picks; an answer due a moment after the exit lands before the soak or the monkey moves the clock. With `--hard 1` a long session counts its context in tokens of its model's window, as Claude Code hands them to the status line, under a compaction setting chosen each day in `settings.json` (the window setup writes, a percent, a model's own window as `/autocompact` writes it, also changed midway through a day, or none): every status line has to show the share of the point Claude Code compacts at, `PreCompact` and a `SessionStart` with source `compact` come at that point and the queue goes on after them, and a context that cannot be brought below its limit ends the turn with `invalid_request` (thrashing, or a prompt too long) or with `max_output_tokens` at the context window limit. Such a session has to be started afresh — never held for a compaction only the context it leaves behind was near — given up on with a notification, or in a cloud session left to the person with a notice, never left waiting with nothing scheduled; an `invalid_request` for anything else is not acted on. Now and then a turn stops at the output token maximum, on an `unknown` or on a `cloud_credential_error`: the session has to be retried on no window but `unknown`, with no notification from the hook that set the retry, or given up on with one, and its relaunch after the output token maximum has to tell it to go on in smaller steps. A session that goes on in its own window after a pause and ends that turn before its runner comes has to go on with its queue from there, its pause over. At the end `tests/continuations.js` checks every relaunch against the answers it could see: no pause continued twice, no session driven by two relaunches at once, no session relaunched after it had gone on by itself, and a reason in the journal for every pause a runner ended without a relaunch. A run of seven days or more also fails when it exercised too little to prove anything: fewer than five stops or five relaunches, no compaction, no move off Fable in noctis's decision journal, or with `--hard 1` fewer than ten chaos injections. |
| `node tests/monkey.js` | A chaos user hammering it in random order; among its moves the clock jumps minutes to hours ahead and the session answers on its own, and three sessions fill their context in tokens up to the compaction point it sets in `settings.json` and moves, with the status line's share checked, the compaction hooks at the point and turns that stop with the context full (`invalid_request`, or `max_output_tokens` at the context window limit) or another `invalid_request` held to the soak's outcomes (observe mode journaling what it would do and giving nothing up); a turn that stops at the output token maximum, on an `unknown` or on a `cloud_credential_error` has to be set to retry with no notification from that hook or from the runner that resumes it, or given up on with one and nothing left waiting, and an account error has to leave nothing waiting and be journaled exactly when it is notified. Its `claude` and the check at the end are the soak's. |
| `node tests/hygiene.js` | Control bytes, invisible characters, executable bits, checksum freshness, version agreement, the state schema, and that `lang.go` still matches `i18n/*.json` — with every translation taking the same placeholders as the English and the `noctis status` labels lining up. Also: `bin/noctis` is still the launcher, it and `bin/darwin/noctis` are executable in git, `bin/SHA256SUMS` lists every binary the plugin ships and no per-CPU macOS folder is left, `bin/darwin/noctis` is a universal binary holding an x86_64 and an arm64 Mach-O executable at page-aligned offsets, with the ad hoc signature Go's linker gives the arm64 one still matching every page (it is read on any system, so a Linux run checks it too), no stray executables over 1 MB outside `bin/`, no leftover `*.tmp`, tests never write `state.json` behind the lock, `ci.yml` runs every fuzz target, every job of a workflow that runs the suites sets `timeout-minutes`, `release.yml` starts only from a passing ci run of a push to main, builds and tags the commit that run tested and skips a version whose tag exists, no `package.json` sits at the root next to a lockfile (Claude Code would run an install in every cached copy), no mixed tab/space indentation in Go, and `hooks/hooks.json` names at most one hooks module, a file inside the plugin named like code; the version is compared across `plugin.json`, `marketplace.json` and `store.go`. |
| `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test .` | `tests/lean.test.ts` under Claude Code's own test kit for hooks modules (run with 2.1.289, 74 tests): the trimming rules on fixed conversations, the `compaction` keys read with wrong types and ranges, and the lean module driven twice — by a stand-in `$`, and through the kit's engine, where the test's own hooks stand for Claude Code's core: with prompt caching off (`DISABLE_PROMPT_CACHING`) a compaction reaches the module, core receives the trimmed rows and a precompute is declined; with it on core receives the engine's rows and the precompute; a turn that ends `compaction.earlyAtPercent` of the way to the compaction point asks for a compaction, the point reckoned as Claude Code reckons it (the model's own `autoCompactWindow` in the settings included, under a provider's spelling of the model too, the settings files laid over each other as Claude Code lays them, and a reply limit below 20000), and so does one next to the weekly pause point; one short of it, one next to the 5-hour limit and one with `autoCompactEnabled` false in `~/.claude.json` do not. Without the variable the command only prints that hooks modules are off. `node tests/lean.js` runs it with the two validations, in a throwaway `CLAUDE_CONFIG_DIR`, and says why when it skips. |
| `node tests/gotest.js` | The Go tests, run as parallel processes: `go test ./...` runs the same tests one after another and waits out every sleep in them (243 s on a 4-CPU Linux machine, where this took about 20 s). It builds the test binary once, splits the top-level tests into shards by the seconds in `tests/gotest-durations.json` (the longest first, each onto the shard with the least work; a test the file does not list counts as 0.1 s) and runs the shards at once, four per CPU and at most 16, each in the package folder with its own `TMPDIR`, `TEMP` and `TMP` and without the caller's `HTTPS_PROXY`, `HTTP_PROXY` or `NO_PROXY` (a few tests would write a file into the package folder, which the shards share). It prints a line per shard, the wall time and the slowest tests, and the whole output of a shard that fails; any failure, panic, timeout (10 minutes a process, as in `go test`) or build error exits non-zero. `--run`, `--race`, `--cover` (with `--coverprofile <file>` for the merged profile) and `-v` work as in `go test`, `--shards N` sets the number of processes, and `--record` rewrites the durations file after a run in which every test passed; another Go package, should one appear, runs under a plain `go test` beside the shards. The tests: unit tests for the decision core, the scheduler and the message catalogs; the naming of models and the window each takes, against the 1547 names and 870 windows Claude Code 2.1.289's own code gives (`go/cmd/noctis/testdata/claudecode-models.json`), for the engine and for the lean module run with Node, and the point the lean module reckons from one to four settings files laid over each other against the engine's, for 3000 random sets; plus the fuzz targets (their seed corpora run as tests; CI fuzzes every target `go test -list '^Fuzz'` finds for 30 s on ubuntu), four structural tests that fail the build: a function nothing calls or only tests call, a field set and never read, a parameter passed and discarded, a host capability flag nothing reads; a language corpus of 410 prompts (25 in each of the fourteen languages, and 60 English prompts with words other languages use) none of which may be read as another language, and none detected today may drop back to undecided — `go test ./cmd/noctis -run LanguageCorpus -v` prints its precision and recall; and a router corpus of 208 prompts (the 88 it already had, and 120 labelled ones: 60 asking for work on the user's own code, 60 research, in English and Turkish) in which every prompt the router places right today must stay placed, in a fresh session and in a coding one — `go test ./cmd/noctis -run RouterCorpus -v` prints how much own work stays on the main model and the precision and recall of the research it routes. |
| `node tests/coverage.js` | How much of the Go source the suite actually reaches, measured by running the lab against a `go build -cover` binary and merging that with the unit profile. linux/amd64 only; while it runs it replaces `bin/linux-amd64/noctis` with an instrumented build and rewrites `bin/SHA256SUMS`, restoring both on exit. `--uncovered` lists the functions nothing reaches, `--html <file>` writes an annotated source page. |

Two environment variables for the suites: `NOCTIS_BINARY=<path>` runs them against another binary instead of `bin/<os>-<arch>/noctis` (`bin/darwin/noctis` on macOS), and `NOCTIS_CHAOS_FULL_DISK=<mount point>` gives `chaos.js` a small filesystem to fill for the real out-of-space case (skipped without it).

**CI.** `.github/workflows/ci.yml` runs on every push and pull request, as jobs that all start at once. The binaries job (ubuntu) builds all six targets from source with `node scripts/build.js` and fails unless the committed binaries and `bin/SHA256SUMS` match them byte for byte, or if the build writes a file that is not committed. The unit job runs on ubuntu, windows and macos: `gofmt` (ubuntu), `go vet`, `node tests/gotest.js` and hygiene (whose `i18n.js check` needs `gofmt`). The fuzz job (ubuntu, in two parts that take the targets alternately) fuzzes each target `go test -list '^Fuzz'` finds for 30 s, one after another. The lab job runs the suites against the binaries committed in `bin/` on ubuntu, windows and macos, in two groups of about the same length on each: the scheduler and the lab; and contract, chaos, `soak.js --days 2 --seed 11 --hard 1`, `torrent.js --jobs 600 --accounts 3 --seed 11` (not on Windows) and the monkey on seeds 7 and 23 with 200 rounds each. The lab waits for no build, and the run still fails when the binaries job finds a committed binary stale. The binaries job may take 15 minutes, a unit or fuzz job 20 and a lab group 30 before GitHub stops it. When a run for a push to main passes and the version in `.claude-plugin/plugin.json` has no tag yet, `.github/workflows/release.yml` builds that commit's binaries from source with `node scripts/build.js`, checks them against `bin/SHA256SUMS`, attests them and publishes the GitHub release, which creates the tag `v<version>`: nobody pushes a version tag. Once a week `.github/workflows/real-tools.yml` installs the real Claude Code, Codex and Copilot CLIs, checks that the main flags the plugin passes are still there and that `codex app-server` answers the handshake, runs the lab again — with a `claude` on PATH, so the lean module's validation and kit tests run there too — and opens an issue when a check fails; it never signs in or runs a model.

Measured for 7.0 (Linux, the CI commands above): lab 582/582 · contract 134/134 · chaos 64/64 (69/69 with `NOCTIS_CHAOS_FULL_DISK` on a 2 MB tmpfs) · scheduler 24/24 · `go test` passing, with `gofmt` and `go vet` clean for linux, windows and darwin · soak, torrent and both monkey seeds passing. The torrent put **600 jobs and 3 268 hooks** through three accounts: 499 sessions stopped before the wall, all 499 parked, none let past a threshold, median hook 10.4 ms (p95 59.2 ms) with an average `state.json` of 173 KB. The two-day hard soak ended with 0 breaches and 0 anomalies (hook p50 8 ms, p95 18 ms). **86.6% of statements covered** (6 961 of 8 035; `go test` alone 64.6%, the lab alone 73.4%).

From the 5.5.0 run, larger than CI's: **2 000 sessions and 9 768 hooks through the torrent with 0 leaks**, median hook 17.7 ms · 0 breaches and 0 anomalies over 7-day hard and 14-day hard soaks · monkey clean on seeds 41 and 77 · 80.5% of statements covered.

What a hook costs, measured for 7.0 rather than asserted (Linux, a Node process starting each call with its payload on stdin, medians of 60 calls): when the binary is called directly, as in a clone install, a `UserPromptSubmit` hook takes 5.2 ms, a `Stop` hook 4.0 ms and a status-line refresh 4.7 ms; through the `bin/noctis` sh launcher that marketplace installs on macOS and Linux run, 11.6, 10.6 and 11.4 ms. Measured again for 7.3.1 the same way (two runs): run directly, `UserPromptSubmit` 5.4–5.7 ms and `Stop` 4.0–4.4 ms; through 7.3.1's launcher, which starts no other program on Linux, 7.0–7.1 and 5.3–6.0 ms; through 7.3.0's, 11.3–11.7 and 10.2–10.9 ms. Measured for 7.3.2 over 120 calls (two runs) with a 264 KB `state.json`, run directly: `UserPromptSubmit` 9.5–9.9 ms and `Stop` 8.0 ms, where 7.3.1 took 14.5–15.4 and 11.0–11.1; an `Edit` or `Write` hook 3.9–4.9 ms (8.0–8.6), and a status-line refresh that brings nothing new 9.0–9.4 ms (10.9–11.2), without rewriting `usage.json`. Measured for 7.4.0 alongside 7.3.2 in the same runs, with that state after one `UserPromptSubmit` has written it, which 7.4.0 keeps at 85 KB by moving its used checkpoints to `used-checkpoints.json`: `UserPromptSubmit` 7.8–8.2 ms and `Stop` 6.2–6.5 ms where 7.3.2 took 10.1–10.2 and 8.2–8.3, and a status-line refresh 6.8–7.0 ms (8.7–9.0); with a small state the two are within 0.1 ms. Measured for 7.5.0 alongside 7.4.0 over 300 calls of each event, with a 77 KB `state.json`: run directly, `UserPromptSubmit` 6.89 ms and `Stop` 6.09 ms where 7.4.0 took 7.75 and 6.92, and a status-line refresh 5.54 ms (7.76); through the launcher, which now starts hooks and refreshes with `GOMAXPROCS=1`, 7.65, 6.84 and 6.49 ms (8.63, 7.83 and 8.85); with a 648-byte state every event is 0.2–0.4 ms faster, and `noctis version`, which does no more than load the config, takes 4.28 ms run directly and 5.25 ms through the launcher. Measured for 7.5.1 alongside 7.5.0 and 7.4.0, with no usage reading on disk and the lab's stand-in for the usage endpoint answering at once (medians of two runs of 20 calls, the hook process alone): a `SessionStart` hook that waits for the answer takes 6.56 ms, where 7.5.0, which waited for a refresher it had started, took 9.83 and 7.4.0, fetching in the hook, 6.59; with the endpoint hanging it returns after 1.5 s, as in 7.5.0, where 7.4.0 took 5.0 s. Measured for 7.5.2 alongside 7.5.1, with native runners off as in the labs (medians of four runs of 40 calls, the hook process alone): a `StopFailure` hook takes 17.87–19.51 ms with the project in a git repository, where 7.5.1, which also started `git rev-parse` and asked `systemctl`, took 23.57–25.75, and 14.61–15.60 ms outside one (18.52–20.15); in each run 7.5.2 was 5.4–6.5 and 3.9–4.9 ms faster. The cost also scales with the size of `state.json` — measured for 5.5.0, 1 KB of state was a 5 ms hook and 313 KB a 31 ms hook — which is why the state file is pruned rather than left to grow.

A 429 in `claude -p`, measured for 7.1.0 against the real Claude Code 2.1.281 (`claude -p` against a local server on 127.0.0.1 that answers 429, a dummy key and no network, noctis installed into a throwaway `CLAUDE_CONFIG_DIR` with `noctis install`): Claude Code starts the asynchronous `StopFailure` hook while it is already shutting down and waits for it only when the hook registered in time; otherwise the hook gets SIGTERM 6–41 ms after it starts. Doing the work inside the hook kept the retry and its relaunch in 100 of 120 runs of the fast path (no OAuth token, no git repository), doing the durable part first in 26 of 40, and handing the work to a detached copy in 108 of 110. With a usage endpoint that never answers, `claude -p` waited 5.8–7.7 s for a hook that did the work itself and exits after 0.7–1.3 s with the hand-off. `TestAClaudePrintModeStopFailureOutlivesTheTeardownThatEndsItsHook` replays that teardown: SIGTERM to the hook, SIGKILL to its process group and the `SessionEnd` hook while the copy still waits on the usage endpoint.
