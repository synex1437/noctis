# Tests

The suite behind the numbers in the README: what each run asks, what CI runs, and what the latest runs measured.

Tests, each asking a different question:

| | |
| --- | --- |
| `node tests/contract.js` | Runs every hook in `hooks/hooks.json` the way Claude Code runs it — resolving `${CLAUDE_PLUGIN_ROOT}`, spawning that command with those arguments. Every other suite runs the platform binary directly with `hook` and a payload, never through the command the manifest declares. It also drives the `bin/noctis` launcher with a fake `uname`: Linux and macOS on both CPUs, Git Bash, MSYS and Cygwin (which get the Windows binary), an unsupported CPU and an exported `CDPATH`. |
| `node tests/lab.js` | 582 black-box checks on Linux (the 7.0 run) against the binary, with a fake `claude`, `codex`, `agy`, `droid`, `copilot`, `gh` and a usage endpoint in a separate process. Each lab checksums its own snapshot of the tree, so a local build runs as it is and no suite rewrites the repository's `bin/SHA256SUMS`; a suite that crashes after its mock server started exits 1 at once and takes the mock with it. Its lean scenario checks that an installed copy carries the hooks module `hooks/hooks.json` names and, when a `claude` 2.1.281 or newer is on PATH, runs `node tests/lean.js`: `claude plugin validate --strict` on the plugin (which must report the module hooking `session.start`, `session.compact` and `turn.complete`) and on the marketplace, then the kit tests below; otherwise it prints why it skipped them. |
| `node tests/torrent.js` | Thousands of long sessions at once. Asks the two questions only volume answers: does the guard ever let a session past the wall, and what does it cost per hook. |
| `node tests/chaos.js` | The failures a real machine produces: 429/403/500, invalid JSON, a body cut halfway, a chunked response cut before its terminating chunk, TLS that will not negotiate, a genuinely full disk (only with `NOCTIS_CHAOS_FULL_DISK`), and state files written by older versions. |
| `node tests/scheduler.js` | Runs the scheduler a real user on this platform gets: a `systemd-run` stand-in on Linux, a `launchctl` stand-in on macOS, the real Task Scheduler on Windows. A parked session is relaunched by the timer with nobody watching, and cancel removes the entry. On Linux and macOS the launchd plist is also parsed with Python's `plistlib`. The `launchctl` stand-in answers `launchctl list` from the jobs it has loaded, and the job that ran a resume must boot itself out afterwards; the launchd path has run only against this stand-in, never on a real Mac. |
| `node tests/soak.js --days 14 [--hard 1]` | A multi-day run (7 days by default, 14 here) of two accounts; `--hard 1` injects 20 kinds of chaos. |
| `node tests/monkey.js` | A chaos user hammering it in random order. |
| `node tests/hygiene.js` | Control bytes, invisible characters, executable bits, checksum freshness, version agreement, the state schema, and that `lang.go` still matches `i18n/*.json` — with every translation taking the same placeholders as the English and the `noctis status` labels lining up. Also: `bin/noctis` is still the launcher and executable in git, no stray executables over 1 MB outside `bin/`, no leftover `*.tmp`, tests never write `state.json` behind the lock, `ci.yml` runs every fuzz target, every job of a workflow that runs the suites sets `timeout-minutes`, no `package.json` sits at the root next to a lockfile (Claude Code would run an install in every cached copy), no mixed tab/space indentation in Go, and `hooks/hooks.json` names at most one hooks module, a file inside the plugin named like code; the version is compared across `plugin.json`, `marketplace.json` and `store.go`. |
| `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test .` | `tests/lean.test.ts` under Claude Code's own test kit for hooks modules (run with 2.1.282, 66 tests): the trimming rules on fixed conversations, the `compaction` keys read with wrong types and ranges, and the lean module driven twice — by a stand-in `$`, and through the kit's engine, where the test's own hooks stand for Claude Code's core: with prompt caching off (`DISABLE_PROMPT_CACHING`) a compaction reaches the module, core receives the trimmed rows and a precompute is declined; with it on core receives the engine's rows and the precompute; a turn that ends at `compactAtPercent` asks for a compaction, and so does one next to the weekly pause point; one below it, one next to the 5-hour limit and one with `autoCompactEnabled` false in `~/.claude.json` do not. Without the variable the command only prints that hooks modules are off. `node tests/lean.js` runs it with the two validations, in a throwaway `CLAUDE_CONFIG_DIR`, and says why when it skips. |
| `go test ./...` | Unit tests for the decision core, the scheduler and the message catalogs, plus five fuzz targets (seed corpus under `go test`; CI fuzzes each 30 s on ubuntu), four structural tests that fail the build: a function nothing calls or only tests call, a field set and never read, a parameter passed and discarded, a host capability flag nothing reads; a language corpus of 410 prompts (25 in each of the fourteen languages, and 60 English prompts with words other languages use) none of which may be read as another language, and none detected today may drop back to undecided — `go test ./cmd/noctis -run LanguageCorpus -v` prints its precision and recall; and a router corpus of 208 prompts (the 88 it already had, and 120 labelled ones: 60 asking for work on the user's own code, 60 research, in English and Turkish) in which every prompt the router places right today must stay placed, in a fresh session and in a coding one — `go test ./cmd/noctis -run RouterCorpus -v` prints how much own work stays on the main model and the precision and recall of the research it routes. |
| `node tests/coverage.js` | How much of the Go source the suite actually reaches, measured by running the lab against a `go build -cover` binary and merging that with the unit profile. linux/amd64 only; while it runs it replaces `bin/linux-amd64/noctis` with an instrumented build and rewrites `bin/SHA256SUMS`, restoring both on exit. `--uncovered` lists the functions nothing reaches, `--html <file>` writes an annotated source page. |

Two environment variables for the suites: `NOCTIS_BINARY=<path>` runs them against another binary instead of `bin/<os>-<arch>/noctis`, and `NOCTIS_CHAOS_FULL_DISK=<mount point>` gives `chaos.js` a small filesystem to fill for the real out-of-space case (skipped without it).

**CI.** `.github/workflows/ci.yml` runs on every push and pull request. The build job (ubuntu) checks `gofmt`, runs `go vet` and `go test`, fuzzes each target for 30 s, builds all six targets from source and fails unless the committed binaries match them byte for byte. A second job then runs on ubuntu, windows and macos: `go vet` and `go test`, hygiene, contract, chaos, scheduler, the lab, `soak.js --days 2 --seed 11 --hard 1`, `torrent.js --jobs 600 --accounts 3` (not on Windows) and the monkey on seeds 7 and 23 with 200 rounds each. The build job may take 20 minutes and each platform job 120 before GitHub stops it. Once a week `.github/workflows/real-tools.yml` installs the real Claude Code, Codex and Copilot CLIs, checks that the main flags the plugin passes are still there and that `codex app-server` answers the handshake, runs the lab again — with a `claude` on PATH, so the lean module's validation and kit tests run there too — and opens an issue when a check fails; it never signs in or runs a model.

Measured for 7.0 (Linux, the CI commands above): lab 582/582 · contract 134/134 · chaos 64/64 (69/69 with `NOCTIS_CHAOS_FULL_DISK` on a 2 MB tmpfs) · scheduler 24/24 · `go test` passing, with `gofmt` and `go vet` clean for linux, windows and darwin · soak, torrent and both monkey seeds passing. The torrent put **600 jobs and 3 268 hooks** through three accounts: 499 sessions stopped before the wall, all 499 parked, none let past a threshold, median hook 10.4 ms (p95 59.2 ms) with an average `state.json` of 173 KB. The two-day hard soak ended with 0 breaches and 0 anomalies (hook p50 8 ms, p95 18 ms). **86.6% of statements covered** (6 961 of 8 035; `go test` alone 64.6%, the lab alone 73.4%).

From the 5.5.0 run, larger than CI's: **2 000 sessions and 9 768 hooks through the torrent with 0 leaks**, median hook 17.7 ms · 0 breaches and 0 anomalies over 7-day hard and 14-day hard soaks · monkey clean on seeds 41 and 77 · 80.5% of statements covered.

What a hook costs, measured for 7.0 rather than asserted (Linux, a Node process starting each call with its payload on stdin, medians of 60 calls): when the binary is called directly, as in a clone install, a `UserPromptSubmit` hook takes 5.2 ms, a `Stop` hook 4.0 ms and a status-line refresh 4.7 ms; through the `bin/noctis` sh launcher that marketplace installs on macOS and Linux run, 11.6, 10.6 and 11.4 ms. The cost also scales with the size of `state.json` — measured for 5.5.0, 1 KB of state was a 5 ms hook and 313 KB a 31 ms hook — which is why the state file is pruned rather than left to grow.

A 429 in `claude -p`, measured for 7.1.1 against the real Claude Code 2.1.281 (`claude -p` against a local server on 127.0.0.1 that answers 429, a dummy key and no network, noctis installed into a throwaway `CLAUDE_CONFIG_DIR` with `noctis install`): Claude Code starts the asynchronous `StopFailure` hook while it is already shutting down and waits for it only when the hook registered in time; otherwise the hook gets SIGTERM 6–41 ms after it starts. Doing the work inside the hook kept the retry and its relaunch in 100 of 120 runs of the fast path (no OAuth token, no git repository), doing the durable part first in 26 of 40, and handing the work to a detached copy in 108 of 110. With a usage endpoint that never answers, `claude -p` waited 5.8–7.7 s for a hook that did the work itself and exits after 0.7–1.3 s with the hand-off. `TestAClaudePrintModeStopFailureOutlivesTheTeardownThatEndsItsHook` replays that teardown: SIGTERM to the hook, SIGKILL to its process group and the `SessionEnd` hook while the copy still waits on the usage endpoint.
