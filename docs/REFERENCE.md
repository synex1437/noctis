# Noctis — reference

The [README](../README.md) says what the plugin does and how to install it, and [the guide](GUIDE.md) how it behaves and how to undo what it changes; this page lists every command, configuration key, host adapter and file.

## Commands

Two flags work with every command: `--account <dir>` is the account folder whose `noctis/` data is used (default `CLAUDE_CONFIG_DIR`, else `~/.claude`; when `--host` or `NOCTIS_HOST` names another tool, that tool's home), and `--host <id>` picks the host adapter (`claude`, `codex`, `antigravity`, `droid`, `copilot`). `setup` and `install` configure every account named with `--config-dir` or `--account` (both can be repeated, a leading `~` is expanded, duplicates are dropped). Flags are written `--flag value` or `--flag=value`; `-h` and `-?` print the help, as `--help` does, and `-v` prints the version, as `--version` does. An unknown `--host` or `NOCTIS_HOST` makes any command you run exit 2 with the list of valid ids, and a valid `--host` wins over a bad `NOCTIS_HOST`; the commands a host or noctis itself starts (`hook`, `statusline`, `resume`, `sleeper`, `queue-wake`, `digest-run`, `ensure`, `release-check`, `webhook`, `selftest-mark`, `state-write`, `refresh`) ignore the bad value and use the configured host, Claude Code by default.

| `doctor` | — | Checks the wiring and says what to fix; exits 1 when something needs fixing. Its first line names the noctis version and the platform, so a pasted report says which build wrote it. Only `errors.log` entries from the last 24 hours count as a problem, and the latest of them is shown redacted as in `report --bundle`; older ones show as OK with the time of the latest. A status line, or another tool's hook file, that runs a noctis binary which no longer exists fails its line. On macOS and Linux with `resume.mode` `window`, a line names the window an automatic relaunch opens in (the `resume.terminal` template, `tmux`, `Terminal` or the desktop terminal it finds), or says that a relaunch runs headless here, where nobody sees it, and how to change that: run claude inside tmux, or set `resume.terminal` |
| `selftest` | `--skip-task` | The doctor checks, plus the Claude Code version against the tested range, the time since the last hook, the speed of one hook call, a test notification, and a check that a background run fires: on Windows a real Task Scheduler task it waits for (a minute or two; `--skip-task` skips it), elsewhere a detached process. It ends with the doctor's verdict and exits 1 when a check failed; when no desktop notifier can start it says so, and that alarms stay silent there, instead of reporting a notification. Its own hook call does not count as a hook pulse, and it is never paused or moved to another model, even past a pause point or the scoped threshold, so it leaves no wait, decision-journal entry or checkpoint behind |
| `check` | `--json`, `--sid <id>` | The exit-code gate described below; `--sid` judges with that session's model and takes the whole id or a start of it at least 4 characters long that fits one session (one that fits several lists them and exits 2), `--json` prints the facts behind the verdict |
| `report` | `--days N` (7, at most 3650), `--json`, `--html [file]`, `--bundle [file.zip]` | Tokens and list-price cost from the transcripts under `<account>/projects`. `--html` writes one self-contained page in the language noctis speaks (to stdout without a file name). `--bundle` writes a diagnostic zip instead (default `<account>/noctis/noctis-bundle-<time>.zip`): doctor output, log tails, state, used checkpoints, usage and config, with tokens, passwords in URLs, webhook URLs in any form (also as older versions logged them), `statusline.chainCommand`, `queue.verifyCommand` and `queue.verifyEachCommand` redacted wherever they appear (also when one holds a path in your home folder or spaces at either end), `resume.terminal` in `config.json`, and your home folder shown as `~`; in `state.json` a prompt parked until a reset becomes `<redacted prompt, length N>`, the subject of an open task `<redacted task, length N>` and each field a recent workflow was launched with (its name, script, script path, description and arguments) `<redacted workflow <field>, length N>` (a `state.json` that is not a JSON object is left out, with a line saying so), and each list under `permissions` in `settings.json` becomes `<redacted list, length N>` — project paths and whatever the logs hold stay, so read it before you share it |
| `queue import` | `--repo owner/name` (or `host/owner/name`, or the repository's URL), `--label name`, `--author login1,login2`, `--file TASKS.md`, `--limit N` (200, per author), `--cwd <dir>` | Appends open GitHub issues through your `gh` CLI as `- [ ] (P1) #123 Title` under the file's `## GitHub issues` heading, after the last item there (a file with no such heading outside a code block gets one at its end) — with `--repo`, or when the file lies outside the git checkout `--cwd` is in (the repository then comes from the issues' URLs, `host/owner/name` off github.com), as `- [ ] (P1) owner/name#123 Title` — priority from labels; line breaks, other control characters and invisible characters in a title become spaces. The file is written only when an item is added or rewritten, in one step, with its own line endings and byte order mark. Only issues you opened are taken: your login comes from `gh api --hostname <host> user`, asked on the host of the repository the issues come from (the host a `host/owner/name` repository names, else the host in the issues' URLs) and only when there are open issues; if it cannot be read, nothing is written, gh's reason is printed and the exit is 1. `--author` (comma-separated or repeated, a leading `@` and letter case ignored) replaces that with exactly the authors it names and asks gh for no login, except that `@me` stands for your login on that host. gh lists the open issues of each of those authors (`gh issue list --author`, `@me` without `--author`), up to `--limit` each, so other people's issues never crowd yours out, and a line says when an author's list reached the limit, since older issues may then be left out. Issues by anyone else are left out, and a line says how many and whose. An issue is skipped when an item (checkbox, bullet or `TODO`) already starts with its reference; a mention inside another item, a heading or prose does not count. With `--repo`, or into a file outside that checkout, a bare `#123` item an older import wrote with the same title is rewritten to name the repository. A list without checkboxes (bullet or numbered items, and no checkbox or `TODO:` line) gets no new item, since noctis would then read only checkbox items and the list's own items would drop out of the queue: the import writes nothing, says so and exits 1 until they have checkboxes. An invalid `--repo` or an empty `--author` prints the usage and exits 2. Default file: the folder's queue file, else `TASKS.md`. A file that is a link leading out of its folder (for the default file, out of `--cwd`) is refused with exit 1 and nothing written; a link that stays inside is followed. A relative `--file` is read and written in `--cwd` (the current folder when `--cwd` is not given), as `queue trust` reads it |
| `queue trust` \| `untrust` \| `status` | `--file <path>`, `--cwd <dir>`, `--sid <id>`; `status --json` | Trusts or distrusts a queue file, or says whether it is trusted (see `queue.requireTrust`; a session never brings up a file nobody trusted, so `status` is where to see one waiting); `status` lists the items and lines added or changed since the trust, or says that the trust came from a noctis that recorded none of them, and `trust` of a file that changed since its last trust lists the lines the new trust covers. For a trusted file `status` also counts the open and the done items and names the item a session takes next and how many wait on items not done yet, and gives the file's pace once sessions have ticked 3 of its items each within 6 hours of the one before: the time an item takes, its share of the weekly limit and how many items a whole weekly limit covers, and what the items left (deferred ones included, `(human)` ones not) need of the weekly limit, what is left of it before its pause point (`thresholds.weeklyAll`, or 100 % while that is off) and when they may be done at that pace — after a weekly reset when the week runs out first; until then it says how many such items it has; it sums up what the ticked items took once 3 stops have found items ticked (the context at the tick, median and most, and the compactions and continues without progress on the way; see `queue.escalate`); for any file it lists the items marked `(human)` and the deferred ones with what they wait on, the last 5 decisions Claude noted on it with `queue note` (and how many in all), names the check between items and where it comes from (the file's `noctis-verify` line or `queue.verifyCommand`) or, while nothing names one and `queue.fileVerify` is on, the command the project seems to check itself with, going by its build files (a `check` rule, else a `test` rule, in a Makefile; a `test` script in `package.json`, run with the package manager its lock file names; `go.mod`; `Cargo.toml`; a pytest setup, run through `uv` or `poetry` when their lock file is there; `deno.json`; Gradle; Maven; `mix.exs`; a .NET solution or project) and the `noctis-verify` line that would run it, since noctis never runs a command it only suggests, counts the ticked items no check has passed (all of them while nothing checks the queue), or, while a failing check holds the queue, says instead since when and how to lift the hold (`queue verify`). `status --json` prints the same facts as one JSON object, for a script or a monitor that watches an unattended run: `file`, `trusted`, `legacyTrust`, `open`, `done`, `waiting`, `human`, `deferred`, `changedSinceTrust`, `items` (the open items in the order they are taken), `next`, `humanItems`, `deferredItems` (`text`, `reason`, `until`), `emptyLines`, `unmatched`, `check` (`command`, `fileLine`, `from` — `file`, `config` or empty —, `held`, `heldAt`, `failures`, `unverified` and `ticked` — the ticked items no check has passed, and all ticked items —, and `suggested`, the command a project seems to check itself with while nothing names one), and `pace` (`items`, `secondsPerItem`, `left`, `finishAt`, and with weekly readings `weeklyPerItem`, `weeklyNeeded`, `weeklyRoom`, in percent, the room running to the weekly pause point or to `credits.ceiling` when that comes first; `null` while the pace is not known), and `decisions` (the last 5 noted with `queue note`, each with `at` and `text`); where there is no queue file it prints `{"file":""}`. `trust` and `status` also name each `(after …)` reference in an open item that is written as a tag, an issue or an item number and matches none, which holds nothing back: up to 50, each cut to 40 characters, then a count of the rest. The Stop hook names them once per session, five at most, then a count of the other new ones; it keeps track of the first 500. Other text in the parentheses is not named. `trust` and `status` also name the file's empty checklist lines (a `- [ ] ` with nothing after it) by line number, since those are not items (see `queue.enabled`). The trust is meant to come from a person: when a Bash or PowerShell call of Claude's runs `noctis queue trust`, the PreToolUse hook denies the call, tells Claude to leave the trust to the user and shows the user a notice (also in observe mode). The hook reads the command the way the shell would, so each word is what the program would receive: it applies single, double, `$'…'` and `$"…"` quoting, backslash escapes and line continuations, brace expansion, and the globs that can name the binary or its subcommand (`./bin/n*s`, `t[r]ust`), reads here-documents only outside quotes and comments, and drops comments; for PowerShell it also reads typographic quotes, spaces such as U+00A0, backtick escapes, here-strings, `<# … #>` blocks, the `--%` verbatim flag and argument lists written with commas, `@(…)` or `(…)`. It finds the binary by name or path (a Windows path too), letter case aside, in any command of a list or pipeline, also after `sudo`, `env` or an assignment, inside an `sh -c`, `eval` or `powershell -Command` string and in the command a `noctis job run` is handed, its arguments read by noctis's own parser; a quoted mention such as `grep "noctis queue trust" docs` passes, and so does one in a `#` comment or a PowerShell `<# … #>` block. When the line also hands text to code (a pipe into or a call of `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `pwsh`, `powershell`, `cmd`, `python` or `py`, `node`, `perl`, `ruby`, `php` or `osascript`; `xargs`, unless every `xargs` in the line runs, named without a path, one of `echo`, `printf`, `cat`, `grep`, `egrep`, `fgrep`, `rg`, `wc`, `ls`, `head`, `tail`, `sort`, `uniq`, `cut`, `file`, `stat`, `du`, `basename`, `dirname`, `realpath`, `readlink`, `touch`, `rm`, `mkdir` or `rmdir`, which start no other program; `eval`, `source` or `.`; `iex`, `Invoke-Expression` or `Start-Process` (`start`, `saps`); `env -S`; a `$(…)`, backtick, `<(…)` or `>(…)` substitution, or PowerShell's `& (…)`), quoted text counts as well: a word naming the binary followed by `queue` and then `trust`, options in between skipped, is denied, and with `xargs` a word naming it followed by `queue` when `trust` appears anywhere in the line. A here-document read by `cat`, `tee`, `git` or `gh` that cannot run commands (its delimiter quoted, or no `$(` or backtick in it) is data and is left out, also when the rest of the line runs code (as in `-m "$(cat <<'EOF'`), so a commit or pull-request message written that way may name the command; any other here-document is read as commands. A `!noctis queue trust` typed in Claude Code runs without hooks, so it goes through. Not recognized: a name or command whose text exists only at run time (a variable's value, the output of a `$(…)` or backtick substitution, or text from `printf`, `base64` or similar), a script file that runs the command, and a program not named above that runs a command it is handed; the check stops Claude's direct call and is not a sandbox. Every other shell call gets no answer from noctis. By the same reasoning the PreToolUse hook denies a `Write`, `Edit` or `MultiEdit` of Claude's whose path resolves to noctis's own `state.json` (which holds the trust records), `used-checkpoints.json` (whose records let a session read the note it was handed without a permission prompt) or `config.json` (which sets whether trust is required and any `queue.verifyCommand`), symbolic links and Windows junctions followed, or that reaches one of them under another name (a hard link, or another letter case on a file system that ignores case, as macOS and Windows do by default), and shows the user a notice; the user edits those files themselves or with `noctis setup`. Default file: the queue file in `--cwd` (the current folder), else that session's checklist. A relative `--file` is read from `--cwd`; `trust` and `status` refuse a path that is not a file, change nothing and exit 1, while `untrust` takes any path so a stale record can be removed |
| `queue note` | `<decision>`, `--file <path>`, `--cwd <dir>` | Notes a decision taken on the queue file without asking — an approach chosen over another, the reading Claude took of an item that reads more than one way, something left out or done differently — for you to read: `queue status` gives the last 5 and how many in all, the daily digest the ones noted since the digest before (for a first digest, in the last 24 hours), and the queue instructions a session starts with the last 5, so a fresh context keeps to them. The words after `note` are the text (at most 300 characters). A file keeps its last 50 decisions in `queue-notes.json`; those of a file nothing was noted on for 30 days are dropped at the next note. The queue instructions ask Claude to run it; it changes nothing but that list |
| `queue verify` | `--file <path>`, `--cwd <dir>` | Runs the queue's check between items now (see `queue.verifyCommand`): the file's `noctis-verify` line while the trust covers it, else `queue.verifyCommand`, in the folder the Stop hook last ran it in for that file (before that, the one the Stop hook of a session where you type it would use) and with the time limit (`verifyTimeoutSeconds`) the Stop hook would use. A pass prints the time it took, records the ticked items as checked, lifts a hold — the next session to start or stop there goes on with the file — closes the issues `queue.github.closeOnDone` waited on, and exits 0. A failure prints the exit status and the end of the output, changes nothing (it does not count toward `verifyAttempts` and does not end a hold) and exits 1, as does a queue without a check command, which says how to name one |
| `queue defer` \| `undefer` | `<item>`, `--reason "<what it waits on>"`, `--until 90m\|2h\|3d\|<RFC 3339 time>`, `--all` (`undefer`), `--file <path>`, `--cwd <dir>` | Sets an open item aside that waits on something outside the session — an account, a key, a file or an answer only the user can give — or takes it up again. The item is named by its number (as `(after N)` counts them), by a `#tag` or a GitHub issue such as `#12` or `owner/name#12` (every open item with it, as `(after …)` reads them; `defer` leaves their `(human)` items out) or by a part of its text that only one open item has; a part several items share lists them and exits 1. The deferral is kept in `state.json` with its reason, so the file and its trust stay as they are: the item stays unticked, is not counted as open and is never handed out, and the items that wait for it stay blocked. `--until` ends it by itself at that time; without it the item stays deferred until `undefer` (`--all` for every item of the file) or for 90 days. `--reason` is required: without it, or with an `--until` that is neither a span nor a future time, nothing changes and the exit is 2; a ticked item, or one marked `(human)`, exits 1. Claude may run both: the queue instructions tell it to defer an item it cannot do now and go on with the next one, and to take a deferred item up again when the user says it is ready. When only deferred items, items marked `(human)` and the items that wait for them are left, the Stop hook lets the session stop and names them once, with their reasons (see `queue.enabled`). When a deferral with an `--until` holds back an item that waits for nothing else, the session goes on by itself once the first such deferral ends: if that end is within the time a wait in place may take (see `wait.maxInHookMinutes`), the Stop hook waits for it and then goes on with the item in the same session, telling Claude which deferral ended and what it waited on, with a wake set for just after that end in case the hook is cut off; otherwise a wake set for that end resumes the stopped session the way noctis resumes one after a pause (the limits, a fresh start and the relaunch go the same way), and the stop's notice says when. The wake leaves the session alone if it went on in the meantime, if the queue no longer drives it, is not trusted as it is or is held by a failing check, and if no item is eligible then; a deferral moved later sets it again for the new end, and while noctis is paused it waits for the pause to end, at its time or with `noctis on`. A prompt in that session, or in another one the same queue drives, `/clear` and `noctis cancel` drop it, and `noctis status` lists it as a `queue` wait. With `resume.mode` `none` the wake only tells you; a cloud session (`CLAUDE_CODE_REMOTE`) starts no runner, so there only the wait in place goes on by itself, and a later end waits for the next prompt |
| `job run` \| `list` \| `stop` \| `forget` | `run [--label <name>] [--log <file>] -- <command>`; `stop <id>`; `forget <id>` or `forget --all` | Runs a long command apart from the session — a build, a full test suite, a migration, a download — so neither a tool call's time limit nor the end of the session cuts it off: detached, in the current folder, in a process group of its own on macOS and Linux, its output in `--log` (a relative path is read from the current folder) or in `<account>/noctis/jobs/<id>.log`. One word after `--` is a command line for the shell (`sh -c`; `cmd.exe` on Windows); several words are a program and its arguments, run without a shell; a detached `noctis job exec` runs it and records how it ended; on macOS and Linux it passes a SIGTERM, SIGINT or SIGHUP it gets (`kill` on the pid `job run` prints) on to the command's process group. Everything after the bare `--` belongs to the command, so it keeps its own flags. The job belongs to the Claude Code session whose tool started it (`CLAUDE_CODE_SESSION_ID`); one started anywhere else is only listed. When Claude ends its turn while a job of its session runs and a trusted queue drives the session, the Stop hook waits for it, looking every 10 s, as long as an in-hook wait may (`wait.maxInHookMinutes`, held to the hook's time limit less 30 s and to a limit noctis inferred; no wait where the Stop hook has less than 90 s, as on Codex, Antigravity, Droid and Copilot), then hands Claude how it ended with the last 20 lines of its log (at most 4096 bytes, terminal colors removed, a line that redraws itself shown in its last state); a job whose process is gone without an exit status is reported as such. If the wait runs out, Claude hears what the log shows so far and decides whether to wait on; `noctis off` ends the wait. A session no queue drives is never held: its jobs are reported at its first stop after they end, and a fresh session that took a paused one's place hears of that session's jobs. `list` shows each job's id, state (running, exit status, stopped, ended by a signal, or gone with no exit status: killed, or the machine restarted; a job whose `noctis job exec` alone was killed, as `kill -9` or `taskkill /F` without `/T` do, runs as long as its command does), run time, label and log; `stop` ends a running job's command with everything it started and waits up to 5 s for its end to be recorded, or for the command to be gone when no `noctis job exec` is left to record it; `forget` drops a record (`--all`: every job that ended), leaving a running job untracked and its log in place. A `--log` inside `<account>/noctis/` other than `jobs/`, or one that reaches `state.json`, its backup, `used-checkpoints.json` or `config.json`, also through a link, is refused with exit 2. Records reported or ended over 3 days ago, and any started over 30 days ago, are dropped, and a log in `jobs/` that no record names is removed once it is 3 days old. The queue instructions suggest jobs to Claude only where the Stop hook may wait for one, and never for a server or a watcher |
| `cancel` | `[sid]` or `--sid <id>`: the whole id, or a start of it at least 4 characters long that fits one session (such as the 8-character id `status` and `why` show) | Ends that session's wait, hand-off, failed-relaunch notice and queue wake and removes its scheduled relaunch; with no argument, all of them for every session. An id that fits several sessions lists them and exits 2 with nothing cancelled; an empty one (`--sid` without a value, `--sid ""`) prints `--sid needs a value` and exits 2 with nothing cancelled, as does an option other than `--sid`, `--account`, `--config-dir` and `--host` (`--id`, `--session`, `--sid1a2b3c4d` without its space), which prints `unknown option …`; an id with nothing pending prints `Nothing pending for …` and exits 0; exit 1 when `state.json` could not be saved, with nothing cancelled |
| `off` | `[minutes \| 90m \| 2h \| 1h30m \| 2 hours \| 1 day]` (60) | Pauses the guard for that long: no limit pauses, denied Workflow launches, research routing, checklists from prompts, `/noctis:start` or queue continuation, and a Stop hook waiting for a `noctis job` lets the session stop. The 100 % stop still applies. Waits already set are kept: it lists each one that will still resume on its own — the session's project folder (or its id), kind and window, resume time and the `noctis cancel --sid <id>` that cancels it — and, when two or more are listed and nothing else is pending (no other wait, relaunch, failed relaunch or queue wake that `noctis cancel` would clear too), `noctis cancel` for all. A wait an open session's hook is holding and a relaunch already under way are left out: cancelling the first would let it continue at once. So is a wait that will not resume by itself: with `resume.mode` `none` the reset only notifies, and a wait stored when no scheduler was available (`[manual]` in `noctis status`) is resumed by hand. At most 7 days (10080 minutes); under a minute counts as one. `0`, a negative number, `nan`, `inf`, other words or more than 7 days print the usage and exit 2 with nothing changed; exit 1 when the pause could not be saved |
| `on` | — | Ends `off` now; exit 1, with the pause kept, when `state.json` could not be saved |
| `checkpoint` | `--sid <id>`, `--cwd <dir>` | Prints the latest unused checkpoint (at most 7 days old) for the folder — the current one by default — or for that session, or `NONE`. `--sid` also takes a start of the id at least 4 characters long; one that fits several sessions lists them and exits 2 |
| `model` | `--sid <id>` | Prints the default model, or the model that session runs (`--sid` as for `checkpoint`) |

| `schedule-preview` | `--backend launchd\|systemd\|task\|sleeper`, `--sid <id>`, `--at <epoch>` | Prints the launchd plist, the `systemd-run` command, the Task Scheduler script or the sleeper command a relaunch would register or start, without registering, starting or writing anything (defaults: this machine's backend, the session id `preview`, an hour from now). The `systemd-run` and sleeper lines are quoted so they paste into a shell (the sleeper line as a PowerShell call on Windows). A command you run that crashes prints `noctis <command> crashed: <reason>` with the path of `errors.log` on stderr and exits 1. The commands a host or noctis itself starts exit 0 after a crash, so a hook never fails the session; a crashed status line prints `∞ noctis error (errors.log)`. `webhook` is the exception: you run it yourself to test the webhook, so a crash in it exits 1 with that message too.

`noctis check` is the exit-code gate for crons, CI and other agents: `0` under every threshold, `10` inside the warn band, `11` a threshold is reached (the hooks would pause unattended work right now), `20` no or stale usage data (no reading, or one of the two windows last read longer ago than `usage.staleMinutes`, even while the other one is fresh), `2` an unknown `--host` or `NOCTIS_HOST` or a `--sid` that fits several sessions, `1` a crash of noctis itself (the reason is in `errors.log`). `11` also covers a window at the 100 % ceiling or about to cross it and a Fable session over the Fable threshold; a `budget.hardStop` pause is not reflected. It records nothing and never touches the network.

`report --json` is ccusage-compatible (`daily[]` with `inputTokens/outputTokens/cacheCreationTokens/cacheReadTokens/totalTokens/totalCost/modelsUsed/modelBreakdowns`) and adds `keptOffPrimary` — the tokens subagents spent on other models instead of the primary one (`models.primary`, read without a `[1m]` suffix), what those calls cost at API list prices (`cost`), what they would have cost on the primary model (`costOnPrimary`) and the difference (`savedVsPrimary`, below zero when those models cost more than the primary one); the last two are left out when the primary model has no price (`best`, `opusplan`, or a model neither the built-in table nor `report.pricing` lists). Its `basis` field says what these figures are: an API list-price estimate, not plan quota saved. The text and HTML reports print the difference with that label, and leave the line out when it is not above zero. Costs use the published list prices (informational on a subscription); `report.pricing` in `config.json` overrides or extends the table. A one-hour cache write is priced at twice the input price, a five-minute one at the cache-write price.

## Slash commands and agents

| Inside Claude Code | What it runs |
|---|---|
| `/noctis:setup` | Asks which roles profile you want (unless you pass `--profile` or a role flag) and whether research and writing prompts go to the `noctis:lite` subagent (unless you pass `--router`; the router stays off unless you say yes), then runs `noctis setup --profile …` with that answer as `--router on` or `--router off` and your words written as flags (`search` becomes `--profile search`, a folder `--config-dir <folder>`) |
| `/noctis:status` | `noctis status`, then `noctis why --last 10` |
| `/noctis:pause [minutes]` | `noctis off <minutes>`; the skill turns a duration such as `2 hours` into minutes (default 60, at most one week) |
| `/noctis:resume` | `noctis on` |
| `/noctis:start <file>` | Nothing: noctis reads the file when you type the command, writes its jobs to a checklist of its own and has Claude work through them (see **Queues you start** below); the skill tells Claude to follow noctis's note, or to say that no queue was started when there is none |
| `/noctis:stop` | Nothing: noctis ends the session's queue when you type the command and says how far it got; the prompt never reaches Claude |

While one of these runs, Claude may use the plugin's own binary for that command without asking (for `/noctis:status`, `status` and `why`), and nothing else: any other command it runs meanwhile goes through your permission settings as usual. `/noctis:setup`, `/noctis:pause`, `/noctis:start` and `/noctis:stop` start only when you type them; Claude cannot start them itself, even when a file it reads asks it to.

These prompts pass the pause point, though not the 100 % ceiling (nor a window about to cross it), so you can check, pause or set up the plugin, or start a queue, at a limit; `/noctis:stop` goes through at the ceiling too, and while the guard is paused or the session runs in another window, because it ends the queue in the hook and no turn runs; a tool batch that only runs the plugin's own binary (plain Bash or PowerShell calls with plain arguments, no pipes, redirections or other commands) is not held either. `noctis why` shows them as `control-prompt`, `control-batch` and, at the ceiling, `block-control-prompt`. Your answer to a question the skill asks is an ordinary prompt: like any prompt you type it goes past the pause point, though not the ceiling. Where Claude Code runs without plugins, as on the web, and the skills are copied into the project's `.claude/skills` (or the account's `skills` folder) as `noctis-pause`, `noctis-start` and so on, they are typed `/noctis-pause` and the like: the hook takes them as it takes `/noctis:pause`, the name `noctis why` shows them by, and noctis's notices name each command that has such a copy as it is typed there.

**Queues you start.** `/noctis:start <file>` looks the file up in the project folder (`CLAUDE_PROJECT_DIR`), then in the folder the prompt was typed in; an absolute path and `~/…` work too, and quotes around the name are dropped. The jobs are the file's queue items, read as in a queue file (checkbox, bullet and numbered items and `TODO:` lines, an item wrapped over several lines being one); a file with none of them gives one job per line, leaving out blank lines, headings, horizontal rules, HTML comments, front matter, fenced code blocks and lines that end in `:`, and a line with a done mark (`~~struck~~`, `(done)`, `✓`) counts as a finished job. An empty checklist line (a `- [ ] ` or `TODO: ` with nothing after it) is no job: the start leaves it out of the count, names it by its line in the file and starts nothing from a file that holds only such lines. noctis writes the jobs to `<account>/noctis/queues/<session>.md` as a checklist, finished ones ticked, and leaves the file alone: Claude is told to tick only the checklist and to read the file for any context a job needs. The checklist needs no trust, and priorities, tags and `(after …)` work as in a queue file. It drives the session before a queue file and takes the place of a checklist from a prompt; a prompt you type while it runs does not end it, a list prompt does not replace it, and the session is told again where the checklist and the file are after a compaction, a resume or a relaunch. Nothing starts, and noctis says why, when the file cannot be read as text (missing, not a regular file, or holding a NUL byte), holds no open job, is larger than 1 MB or holds more than 500 jobs, while the guard is paused, and while `queue.enabled` is false; in observe mode the start is only journaled. `/noctis:stop` ends the session's queue, one from `/noctis:start` or from a prompt, deletes its checklist and says how many of its jobs were done; with no such queue it says so, and names the queue file that drives the session (a trusted one, or any while `queue.requireTrust` is off) and how that one stops. `noctis why` shows `start-queue`, `refuse-start-queue` and `stop-queue`.

**Prompts you type at a pause point.** A prompt you type is not parked at a pause point. It goes ahead with a warning, once per window and reset (`⚠ 5h window 93% (threshold 92%): your prompt goes ahead anyway. noctis stops it only at the usage limit.`; the second sentence is left out while `credits.allowPaid` is on), and Claude is told that the prompt runs past the pause point and to start no big new work beyond it; when a burst, a projection from stale data or an imminent compaction brings the pause forward, Claude is told that the usage is still under the pause point and why noctis pauses now. A wait already stored for the session is cancelled with its runner, since you are back at the keyboard. The turn the prompt starts runs to its end: its tool batches, its `Agent` and `Task` calls and its subagents are not held at the pause point; a new `Workflow` still meets its gate. What still parks the prompt, and stops its turn: the credit ceiling (100 %, or a window about to cross it), a pause for missing data (`blind`) and `budget.hardStop`. The turns that start by themselves after yours ends — a queue continuation, a relaunch, a wake — meet the pause point again, and so does a prompt noctis composed. `noctis why` shows `typed-prompt` for the prompt and `typed-turn` for the first batch or subagent call of its turn past the pause point; in `observe` mode they are `would-typed-prompt` and `would-typed-turn`, and nothing is shown. Antigravity has no prompt event, so there every turn meets the pause point.

Four agents come with the plugin. `noctis:lite` does research and writing on the `roles.research` model; it may write only `.adoc .csv .markdown .md .rst .srt .tsv .txt .vtt` files — the PreToolUse hook denies a `Write` to any other file, and to `CLAUDE.md`, `CLAUDE.local.md`, a file named like one of the `queue.files`, anything inside a `.claude` folder, anything inside the account folder (`CLAUDE_CONFIG_DIR` or `--account`, whatever its name; noctis keeps its queues and state there) and anything inside the plugin's own folder, because those files steer the main model — and its frontmatter keeps `Edit`, `MultiEdit` and `NotebookEdit` away from it. The hook follows the path the way the write does: through linked folders (Windows junctions among them) and through a link at its end, also one whose file does not exist yet, and a path with `..` is checked both where it leads past a linked folder and as it reads with the `..` folded. Each check applies to the path as given, to every link at its end and to the file the write lands in; a link the hook cannot follow (a loop, or more than 8 links in a row) is denied. The account and plugin folders are known by the folder itself, so a path that leads into one of them under another name, the folder a `~/.claude` link leads to among them, is denied too. Not covered: a file or folder that `CLAUDE.md`, a queue file or a project's `.claude` is a link to, written under its own name (an `AGENTS.md` that `CLAUDE.md` links to, say), and the files a `CLAUDE.md` pulls in with `@`. `noctis:digest` runs noisy commands (test suites, builds, long logs) on the `roles.digest` model and returns a digest; it never writes files (its frontmatter disallows the file tools, and the hook denies a `Write`). `noctis:deep` takes over a queue item a session got stuck on, on Opus at max effort (`queue.escalate`); it has the tools and the write rules of the main session, and setup leaves its model and effort as they are. `noctis:worker` does one queue item a session hands to a subagent (`queue.subagentAboveTokens`, an item tagged for another model, `queue.escalate` to another model) in a context of its own, on the session's model unless the call names another; it too has the tools and the write rules of the main session, leaves the queue file to the session that called it, which checks its work and ticks the item, and ends with the files it changed and each check it ran with its exit status. The hand-offs name it by its `subagent_type`, so the item gets a fresh context rather than a fork of the session's, which would carry the whole conversation along, and needs no general-purpose agent, which a session may lack; they tell Claude to wait for its result, since a subagent may start in the background. These write limits apply in observe mode too and are not journaled. A hand-made agent named in `router.agent` or `router.digestAgent` has to keep `Edit`, `MultiEdit` and `NotebookEdit` out of its tools the same way, because the hook does not apply this write policy to those calls (it sees `Edit` and `MultiEdit` only for the own-file check below, and never sees `NotebookEdit`); `noctis doctor` and the startup self-check name an agent file that allows one. Unless the router is off, the guard is paused or observe mode is on, a prompt that starts with `lite:` is always sent to `noctis:lite`; one that starts with `main:` or `fable:` never is. A session started with `claude --agent <name>` (or the `agent` setting) is guarded like any other main session; one that runs as the lite agent itself is not told to hand its research to that agent.

**Subagents at a limit (Claude Code).** Subagents and workflow agents meet the pause point and the credit ceiling on their own loop; in the turn of a prompt you typed, only the ceiling (see above). Past the pause point, a subagent's `WebSearch`, `WebFetch`, `Agent`, `Task`, `Workflow` or `Write` call is denied with an instruction to start no new work and report what it has; its first tool batch past that point carries the same instruction, and the next one ends the agent. At the ceiling it is ended at once. Batches that only deliver the report (`SubagentHandback`, `StructuredOutput`) pass, and a subagent's `Workflow` also meets the warn band and the fan-out headroom. Each agent cut short is named — `<type> agent <id> — stopped by the usage limit at <time>; its result is partial`, or `told at <time> to wrap up …; its result may be partial` — in the checkpoint, in the note a relaunch or wake starts with, and in the context after an in-hook wait, so the resumed session redoes that part instead of trusting a saved result. The journal actions are `deny-subagent-tool`, `warn-subagent` and `stop-subagent`. On the other tools, subagents are not guarded this way.

Claude Code hook events wired in `hooks/hooks.json`: `SessionStart` (on `startup` it also runs `noctis ensure`), `SessionEnd`, `UserPromptSubmit`, `PreToolUse` (`WebSearch|WebFetch|Agent|Task|Workflow|Write`, and `Bash|PowerShell|Edit|MultiEdit` for the `queue trust` check below, the check that Claude does not write noctis's own `state.json`, `used-checkpoints.json` or `config.json` and the check of a checklist from a prompt, see `queue.auto`), `PostToolBatch`, `StopFailure` (`rate_limit|overloaded|server_error|model_not_found|billing_error|account_on_hold|authentication_failed`), `Notification` (`quota_auto_resume_fired|quota_auto_resume_stale|quota_auto_resume_disabled`), `PostModelSwitch`, `TaskCreated`, `TaskCompleted`, `PostToolUse` (`Agent|Task`), `Stop`, `PermissionRequest` (`Read|Edit|MultiEdit|Write`; see `queue.auto`), `PreCompact` (asynchronous; while a trusted queue drives the session it counts the compactions of the item in hand, journaled as `count-compaction`). In a run Claude Code treats as non-interactive (`CLAUDE_CODE_ENTRYPOINT` `sdk-cli`, which is `claude -p`, `sdk-ts`, `sdk-py` or `claude-code-github-action`), Claude Code starts the asynchronous `StopFailure` hook while it is already shutting down and does not always wait for it, so there the hook ignores SIGTERM, writes the payload to `<account>/noctis/pending/` and exits after starting a detached `noctis hook --input <file> --account <account>`; that copy stores the checkpoint, the retry and its scheduled relaunch, removes the file and never wakes the session in place. Interactive sessions keep the in-hook path and the same-session wake, and when the copy cannot be started the hook does the work itself. A `SessionEnd` that runs while such a hand-off (younger than an hour) is pending keeps the session's workflow record for the relaunch. On `/clear`, the `SessionEnd` of the cleared session releases a wait its hook was sleeping on (a pause stopped before the `/clear`, or a same-session wake), unless the session is being relaunched, so a conversation you cleared is not resumed; `SessionStart` releases the stopped pause of the folder's session the status line showed last, never a wait whose hook still holds it in another window, and gives the new session that session's model. On `startup` and `/clear`, `SessionStart` hands the new session the latest unused checkpoint of its folder (at most 7 days old), except one whose own session will still be resumed — its wait is pending or its relaunch is running. A checkpoint counts as used once its own session goes on: a prompt there passes the guard, or the guard is paused. A session a relaunch starts in place of a paused one (see `resume.freshAfterMinutes`) is handed only that session's checkpoint, in its prompt. After a compaction (`SessionStart` with the `compact` source), while a trusted queue that is not held drives the session, `SessionStart` adds a note after the queue's directive, read from the queue file, `git status` and noctis's record of the check rather than from the summary: the item in hand, the files changed since the last commit (at most 12 named), how the check stands (none, failed or cut short at its last run, or when it last passed) and, from the second compaction on the same item, how many it has gone through, with a word to hand long test runs, big diffs and wide searches to a subagent. Under `modules` it also names the hooks module `hooks/lean.js`, which Claude Code loads only with function hooks on (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`); it hooks `session.start`, `session.compact` and `turn.complete`. A value of the wrong type or out of range in the `compaction` keys it reads is replaced by the shipped one. While `compaction.lean` is on and prompt caching is off (`DISABLE_PROMPT_CACHING`, the only time it trims), it declines a summary Claude Code computes ahead of time (`precompute`): once the rows are trimmed, Claude Code would discard that summary. A message it trims goes to the summary without Claude Code's handle, so Claude Code rebuilds it from its role, text and tool blocks alone (Claude Code's contract for a rewritten message); a message it leaves alone keeps its handle and stays whole.

A run cut short — past `verifyTimeoutSeconds`, killed by a signal, or ended with status 124 (as `timeout` ends one) or 137 (a kill, as when the system runs out of memory) — says nothing about the code, so the first such run since the last pass runs once more before it counts: at once when the Stop hook has time left for a run as long as the first, else at the next stop while Claude goes on with the next item (the digest says so meanwhile); with no item left to go on with it counts at once. A run after a failed attempt or during a hold counts as it ends. The last send-back before the hold adds that, if the failure cannot be fixed now, Claude should undo the item's changes (keeping them on a branch or in a stash), leave the item unticked, set it aside with `noctis queue defer … --reason` and go on with the next one, so the check passes again without it. After `verifyAttempts` failures in a row the fix first goes once to a stronger model where there is one (see `queue.escalate`); after that, or where there is none, the stop is allowed, you are told once (a notice, and a notification that names `queue.verifyCommand`, or says the check the file names, without quoting the command) and the queue is held: later stops, session starts and relaunches do not continue it. With `verifyAttempts` above 2, a failure whose exit status and end of output match those of the failure right before it (durations, clock times, dates, memory addresses and temporary folders left out) holds the queue at once, since the fix in between changed nothing the check sees; the notice says so, and `noctis why --json` shows `same` on that `hold-queue`. A run cut short, or one that printed nothing, is never the same. A held queue's command runs again at the first stop after you type a prompt, or at once with `noctis queue verify`: if it passes, the queue continues; if it fails at a stop, the queue stays held and you are told again, and `queue verify` changes nothing. The command never outlives the Stop hook: it gets at most what the hook has left less 30 s, which is 30 s where the Stop hook has 60 s (Codex, Antigravity, Droid, Copilot); in Claude Code (21600 s) a wait in place in the Stop hook leaves `verifyTimeoutSeconds` free for it and a longer wait goes to the runner; and a hook time limit noctis inferred from in-hook waits that kept ending early (noted in `errors.log`) cuts it to that limit less 60 s. Its record in `state.json` is dropped after 30 days without a run, and a hold with it. With `queue.github.closeOnDone`, an issue is closed only once a run has passed with its items ticked. `noctis why` shows `verify-queue` (with `cut short: …` for a run that runs once more), `hold-queue` and `allow-stop` (`queue held`); observe mode journals `would-verify-queue`, runs nothing and closes issues without waiting for a run |

**Parallel pauses.** Hooks of one session that pause for the same limit at the same moment — several Agent calls fanned out at once, or the per-call `PostToolUse` hooks of Codex and Droid — share one wait: a pause joins the stored wait when it is for the same window, its reset is within 2 s, it was stored less than 120 s ago and the pause is not a prompt. Every hook then holds until the reset, or until an early reset or fresh data releases the wait. A hook clears only the wait it stored itself; if another pause for the same reset replaced it, it holds on that one, and if a different pause replaced it (another window, or a wait handed to the runner), it stops with that pause's `work saved, auto-resume at …` message, followed by that pause's reason when it did not come from its pause point. `noctis why` logs these as `join-wait` and `wait-replaced`.

**One continuation per pause.** A pause is continued once. What takes it over marks it as continued under the state lock: a `claude --resume` of the session in another window, the runner when it relaunches the session, the Stop hook of the turn a same-session wake started, and the runner when it finds that the session already went on by itself, after a same-session wake or Claude Code's own auto-continue: a prompt or an answer after the pause's reset, which for a turn that failed is the end of the second the failure came in, so what the session wrote just before the failure does not count; after a relaunch that ended with an error before the session answered, an answer from the second it ended in counts too, while the prompt and the API error that relaunch wrote do not; after Fable's weekly cap, where noctis switched the model and parked a relaunch on the fallback model, only an answer from after the second of the switch counts, so a prompt alone, a local command such as `/usage` and the answer of the turn the switch ended do not. Only what reaches the transcript after noctis recorded the pause counts, as the session going on or as the reply to a relaunch, and for a queue wake only what reaches it after the wake was set, so what the session wrote before does not count even when a system clock that went back stamped it later. A hook that still holds that pause in place then stops instead of going on as well, with `⏹ While this window waited, the session went on in another window, so this one stops here and the work does not run twice.`: a prompt is blocked, an Agent call is denied and ends the turn (`continue: false`), a tool batch ends the turn, and the Stop hook lets the stop through. A hook that ends its own wait at the reset and `noctis cancel` leave no mark, so the other hooks holding the same wait go on as before. A runner that finds its pause marked as relaunched by an earlier runner, and an answer from the session since then, drops the pause instead of relaunching the session again (`skip-launch` in `noctis why`): the pause can come back with the backup of a damaged `state.json`, or stay behind when its runner was killed after the session answered. A runner that ends a pause without relaunching the session always leaves its reason there as `skip-launch`, also when Claude Code's own auto-continue resumed the session, when `resume.mode` is `none` and when no usage data came in by the last try. Every step that changes a pause (clearing it, rescheduling its runner, a hook's heartbeat, an early resume, a wake's mark, releasing an interrupted wait) changes it only while it is still the pause it read, with the same start time and holder, never one that took its place meanwhile. `noctis why` logs `continued-elsewhere`.

## Other AI coding tools

The engine is host-independent; a thin adapter per tool writes that tool's hook file, translates hook JSON in and out, reads usage where the tool exposes it, and resumes sessions with the tool's own command. `scripts/install.sh` / `install.ps1` (or `noctis setup` in a terminal) ask **which tool** with a numbered list; `--host <id>` skips the question. The answer can be the number, the id, the tool's full name, or three or more letters that start a word of exactly one tool's name (`ant`, `cop`); an empty answer means Claude Code, and anything else is asked again. On Windows the question appears in a console (PowerShell, cmd, Windows Terminal) but not in Git Bash or mintty, whose stdin is a pipe: pass `-Tool` / `--host` there. `install.ps1 -Tool` takes an id; a display name such as `'Codex CLI'` exits 2 with the list of ids.

Claude Code's relaunch runs in the folder the session started in (its `CLAUDE_PROJECT_DIR` at the pause), not in a subfolder Claude had moved into with `cd`: Claude Code gives a resumed session's hooks the folder it is started in as `CLAUDE_PROJECT_DIR`, so this keeps the session's queue in reach. Claude Code and Codex get the prompt after `--`, so a prompt is never read as an option, and for every tool a prompt that would start with `-` starts with `Continue. ` instead. Every relaunch starts the tool without the session markers Claude Code gives its hooks (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_PID`, `AI_AGENT`, `CLAUDE_EFFORT`, `TRACEPARENT`, `CLAUDE_CODE_ENTRYPOINT`), so the relaunched session carries no marker of the session that paused and starts as a session of its own.

Not supported (checked September 2026): Gemini CLI (consumer access ended June 2026 — use Antigravity CLI), Kiro CLI (`AgentStop` cannot block), Cursor / OpenCode / Amp / Qwen Code (hooks exist but no script-readable limits; queue-only support is on the list), Roo Code (archived), Cline / Goose / Crush (no continue hook).

Install for another tool from the zip or clone: `./scripts/install.sh --host codex` (macOS/Linux) or `.\scripts\install.ps1 -Tool codex` (Windows); the plugin lands in `<tool home>/noctis/plugin/` with its config next to it, and `noctis doctor --host codex` checks the wiring. Uninstall: the same command with `--uninstall` / `-Uninstall` — it removes only the plugin's own hook entries (on Antigravity also the `statusLine` it wrote) and the `<tool home>/noctis/plugin/` copy, and cancels the relaunches still pending; the config and logs next to it stay unless you add `--purge` / `-Purge`.

**Honest status:** the four adapters implement each tool's documented hook, usage and resume contracts and pass the black-box lab against stand-ins of those tools. A weekly CI job (`real-tools.yml`) installs the real Claude Code, Codex and Copilot CLIs and checks that the main flags the plugin passes are still there, and that `codex app-server` answers the handshake; it never signs in or runs a model, and Antigravity and Droid are not checked. No adapter has run a real session end to end yet — smoke tests are in [docs/HOSTS.md](HOSTS.md); reports with the tool's version are welcome.

| File | What it holds |
|---|---|
| `config.json` | Your configuration (the table above) |
| `usage.json` (+ `.bak`) | Status-line captures, per-session model, context (its share and, as `contextTokens`, its tokens) and the version its status line reported, burst history — a stable contract other status lines can read; each window also carries `at`, the time it was last reported, and each session's record (`sessions.<id>`) carries `windows`, the reading its own status line last showed of each window. A `usage.json` that exists but cannot be opened (its permissions, say) is left as it is, and status-line readings are not stored until it can be (`errors.log` says why) |
| `fable.json` | The windows from the last OAuth usage fetch (on Codex, from `codex app-server`), with its error and back-off |
| `release.json` | The last published version the daily check saw |
| `digest.json` | When the last daily digest that went out was sent and, for each queue file it reported on, the items done then, so the next digest names the items ticked since |
| `state.json` (+ `.bak`) | Pending waits, queue wakes and hand-offs, the daily digest's runner and how the last digest went, the checkpoints not used yet, queue trust, the check records, deferrals and pace notes of queue files (the last 25 changes of the done count, with the time and the weekly use then; kept 30 days), what each setup did on them and what their ticked items took (the last 50 notes), the records of `noctis job`, what the router learned, notices already shown; written without indentation. A checkpoint moves here from `state.json` in the state write that uses it up, and stays in `state.json` while this file cannot be written; a record goes 7 days after its checkpoint was made, at the first state write after that, and its note with it unless a newer checkpoint of the session still to be used is in the same file. Written under the `state` lock; a `Write`, `Edit` or `MultiEdit` of Claude's to it is denied, as for `state.json` |
| `queue-notes.json` | The decisions noted with `noctis queue note`, the last 50 of each queue file, and how many were noted on it in all |
| `decisions.jsonl`, `guard.log`, `errors.log` | The journal behind `noctis why`, the full log, and its WARN/ERROR lines — each rotated to `.1` at 512 KB |
| `resume-output.log` | Output of headless relaunches, rotated at 512 KB |
| `hooks-debug.log` | Raw hook payloads, only with `NOCTIS_DEBUG_HOOKS` |
| `checkpoints/<sid>.md` | The checkpoint of each paused session, kept 7 days |
| `queues/<session>.md` | Checklists noctis wrote from long prompts; one is removed when its job is done or you steer the session by hand, otherwise 7 days after it last changed, and never while its session waits on a pause |
| `quiet/<session>.json` | Markers for the quiet fast path |
| `proxies/<session>.json` | The proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and their lower-case forms) of a paused session whose resume launchd or systemd will start, readable only by you (mode 0600); for a resume Task Scheduler will start, also the session's `PATH`, `TZ`, `DISPLAY`, `WAYLAND_DISPLAY`, `TMUX`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS` and `NOCTIS_QUEUE`, which a scheduled task gets no other way. A proxy URL can hold a password, so these stay off the `systemd-run` command line and out of the plist: the runner reads the file and removes it when it starts; cancelling or rescheduling that job removes or rewrites it |

| `lean.json` | The sessions the lean module ran in, the last 50; a session missing from it gets the `ctx ▲` mark and the `/compact` notice |
| `launches/` | Relaunch scripts, pid files, selftest markers. | `jobs/` | The logs of `noctis job run` without `--log`, one `<id>.log` per job; a log no job record names any more is removed once it is 3 days old |
| `pending/` | The `StopFailure` payload of a `claude -p` or Agent SDK run while the detached copy it was handed to stores the retry; removed when the copy finishes. One the copy never removed is swept once it is an hour old, a half-written one after five minutes |
| `runner.cmd` | Windows: the launcher the scheduled task runs; it switches its console to UTF-8 (code page 65001) first, so a profile path with letters such as Ç, ü or Cyrillic still resolves |
| `*.lock` | `state`, `usage`, `fable`, `settings`, `schedule-<hash>`, and `rotate`, held only while a log is moved to `.1`. The exception: a lock more than two minutes old whose recorded pid is a running process counts as hung and is taken over without the `flock` test — also when that process is a new one that got the dead holder's pid |
| `noctis-bundle-<time>.zip` | `noctis report --bundle` without a file name |

## Limits

Usage data comes from Claude Code's official `statusLine` payload (`rate_limits`, Claude Code ≥ 2.1.251) and from the undocumented OAuth usage endpoint, which supplies the scoped bucket and backs up the 5-hour and weekly windows when status-line data is stale — keep an eye on `errors.log` after Claude Code updates; `selftest` reports the tested version range. Same-session wake relies on `asyncRewake`, which is documented as observational; the scheduled relaunch covers the case where it stops working. Lean compaction runs on Claude Code's early-access function hooks (tested with 2.1.281), which may change between releases; without them, compaction is Claude Code's alone.

Long unattended queue work has its own edges. A deferral whose `--until` ends after the Stop hook may wait in place wakes a session that stopped on it only where noctis can start a runner: a cloud session gets none, so there the next prompt, relaunch or session start goes on with the item. The Stop hook waits for a `noctis job` only while a trusted queue drives the session and only where the hook may run long enough (Claude Code); elsewhere Claude hears of the job at its next stop. A relaunch opens in tmux only when the claude that paused ran inside tmux; on a server without it the relaunch runs headless and its output goes to `resume-output.log`.
